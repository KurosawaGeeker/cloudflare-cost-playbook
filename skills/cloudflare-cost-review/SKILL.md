# Cloudflare 成本审查

目标：在业务需求不变的前提下，找出哪个动作触发哪种计费，提出与预算相符的实现，并留下证据。不要把某个事故的 R2/DO 方案推广成所有项目的必选项。

## 先确定审查范围

区分设计、代码审查、事故调查和上线验收。只做用户授权范围内的工作；审查不自动授权部署、停服、创建资源、改套餐或线上压力测试。

优先读当前代码、路由和已有用量记录。询问会影响决策的缺失信息：数据新鲜度、流量/停留时长、日/月预算、失败时允许的行为。可暂用显式假设开展成本模型与本地分析，不把未知值补成确定事实。

## 必须形成的证据

1. **请求地图**：列出 HTML/资产、公共读、个人读、写、OPTIONS、后台发布、重试和所有替代入口。每条注明执行次序、调用计费产品、共享缓存可否绕过计算、源码或配置依据。
2. **成本模型**：正常、增长、异常流量各一份。轮询量约为“可见在线时长 / 间隔”，加首次读取、重试和个人请求；脚本直接请求不受前端退避约束。价目、日期、套餐、单位、免费额度归属和排除项必须列明。
3. **缓存证明**：辨别浏览器缓存、CDN、Workers Cache、`caches.default`、R2、DO/D1。内部命中不能推出外部请求免费；不同节点的相同键不能推出全球锁。以 Worker 调用变化、R2 操作数、缓存头/日志验证实际效果。
4. **防护与费用响应**：指出拦截层级，检查 Workers 默认地址、预览、dev、R2 开发地址及源站入口。应用内 403/429、客户端门禁、CORS 均不能代替收费前防护。预算提醒、CPU 上限、监控检测与自动降级分开验收。
   必须检查账号级全局账单监控，不能只检查单次调用或单个产品。明确跨产品用量费用与固定费用的覆盖范围、分级阈值、接收者、送达演练、主动复查及处置负责人。按当前官方规则核对每条告警的触发频次和统计延迟；同账期单次邮件不能替代持续提醒，原生能力不足时另行实现巡检与升级，未部署则标为待验收。
5. **交付状态**：源码、本地、提交、部署、线上行为、计费窗口分别标记已验证/待验证/不适用。写明证据窗口、采样和剩余风险。

对产品规则先查当前官方资料，见 [Cloudflare 核验点](references/cloudflare.md)。新项目给控制台配置页链接，而非仅 API 规范；不要要求用户在聊天中贴密钥。

## 实施原则

- 公共相同数据可评估静态资产、CDN快照；个性化/授权结果不进入共享公开缓存。缓存 TTL 过期通常等待请求刷新，不是各节点自动按时拉取。
- 让高频公共读避免进入用户动态程序，和在程序内部减少数据库操作，是两个不同优化目标。R2 自定义域名直读需要明确缓存规则，不能通过 Worker 代理后宣称已消除入口费。
- R2 固定键覆盖不需要制造无限版本对象。并发发布仍需协调，读到旧快照与存储一致性分开处理；失败保留旧数据并记录新鲜度，不以动态回退扩大费用。
- 成功写入应先可靠持久化并幂等。普通 Worker 内存不是可靠批量队列。若用 DO/队列聚合，分别核算请求、执行时长、存储与消息，不声称免费。
- Turnstile 的服务端验证保护写入；它不自动保护公共 GET。需要访问挑战时核对 WAF/Pre-clearance，别让 JSON fetch 收到挑战 HTML 后无限重试。
- 费用控制可能有检测/配置传播延迟。没有实际可用硬上限时明确写“不能保证封顶”，同时给降级路径和验证；不要自创不存在的平台能力。

## 算法与输出

可运行随 skill 附带的 [费用计算器](scripts/cost_model.py)，使用 [输入示例](references/example-input.json)。它仅覆盖指定 Workers/R2 用量；D1、DO、日志、WAF、订阅等另算。价格快照用于复算，实际部署前更新。

最终按 [审查记录模板](references/review-record.md) 输出。成本数字是估算时注明假设；事故数字注明来源、窗口和可信度。未通过线上验收不能宣称预算受控或防护完整，也不需要为了审查擅自恢复已停服服务。
