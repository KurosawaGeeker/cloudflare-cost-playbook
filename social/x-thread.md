# X 长帖发布稿：一个投票站的 26 亿次请求

以下为逐条可发布的中文长帖。数字截至 2026-10-04，费用是累计用量，不是已确认扣款。发布入口由作者自行选择；本文件没有发布，也没有构造尚不存在的仓库 URL。

## 1/16

用 AI 做了一个投票站：两张图、两个按钮、实时票数。

后来查 Cloudflare，投票 Worker 近 7 天约 26.1 亿次调用。账号截至 10/4 的累计用量费 $816.52，其中 96.19% 是请求费。

做过验证码、限流、缓存，账单为什么还会这样？我把这次事故完整复盘了。

## 2/16

先限定口径：

$816.52 是 9/11–10/10 账期内，截至 10/4 的账号用量费，不是已确认扣款。

26.1 亿是指定 Worker 近 7 天调用；26.3 亿是账号账期请求，两者不能混用。

请求也不等于真人访问，不能拿这些数字直接卖广告曝光。

## 3/16

最初我要求的是“单页、实时投票、挂 GitHub Pages”。

共享票数需要后端，于是实现增加了 Worker + D1，后来又迁到 Cloudflare 自定义域名。

从静态页面变成公开动态服务时，应该重新确认实时性、预算和异常流量成本。

这不是用户第一个 prompt 没写 Cloudflare 的锅。

## 4/16

我很早问过“访问量巨大，账单会爆炸吗？”

助手解释过请求收费，也说过 50 ms CPU 上限不是月费硬上限。

所以不能说完全没提醒。

遗漏在于：提醒之后，没有落实费用预算、收费前拦截、持续监测和降级验收。

## 5/16

先出的是计票问题。

初版用浏览器随机 UUID 去重：每个 UUID 一票，但换 UUID 就能继续投。

一晚记录了 455 万多票，D1 也实际报过排队过久。

后来加服务端 Turnstile、限流、缓存、退避并归档旧票。这修了业务和数据库压力，但没修完整的费用边界。

## 6/16

读取路径是：

用户 GET → Worker → 内部缓存 → 返回 JSON。

缓存命中时可以不查 D1，但已经进入 Worker。

“不执行 SQL”和“不产生 Worker 入站调用”不是一回事。

本次请求费 $785.40，CPU 费 $31.12。只降低 CPU，解决不了主费用。

## 7/16

不要看到“缓存”两个字就放心。

Worker 内 Cache API：减少 SQL 和部分执行。

当前平台 Workers Cache：命中可跳过脚本，但官方仍按请求计费。

不经过该 Worker 的静态/CDN 路径：才可能避开它的入口调用，另算回源和存储成本。

要问：缓存挡住了哪一种计费操作？

## 8/16

保护版约每 5 秒查一次票数。

一个持续可见页面，一天约 17,280 次读取。100 个页面持续 30 天，就是约 5,184 万次。

页面隐藏暂停、错误退避都有价值，但直接打接口的脚本不必遵守。

没有证据表明这里有前端零间隔死循环；轮询本身已经是成本放大系数。

## 9/16

验证码保护投票资格，IP 配额保护新票，缓存保护数据库。

公开 GET 不需要投票，就能继续读取。

即使开网页先弹验证码，脚本也能跳过页面。即使 Worker 返回 403，请求也可能已经进了收费程序。

需要核对的是拦截层级，不只是响应状态码。

## 10/16

边缘保护要看完整入口。

主域名、workers.dev、预览、dev、备用域名都要列出来。

某个主域名规则生效，不代表其他入口自动受保护。

测试站也不是天然免费：如果静态资源先跑 Worker，它们同样可能增加程序调用。

验收要对照规则事件与 Worker 指标。

## 11/16

拟议改进：读写分开。

投票 → 服务端验证 → 可靠持久化。

受控发布器 → 共享快照。

用户读快照 → 独立静态/CDN 入口，不再调用投票 Worker。

批量发布的是公开结果，不能把已承诺成功的票攒在普通 Worker 内存里等着落库。

这是方案和本地示例，不是原站已经线上验证完成的修复。

## 12/16

R2 也不是万能省钱答案。

按同样 26.1 亿 GET 测算，假设月免费读取额度可用：

最终 99% 不到 R2，读取费约 $6.12。

缓存完全失效，读取费约 $936。

这只算读取，不是总账单。

真正需要证明的是实际回源数，不能拿旧 Worker 的缓存命中率替新方案担保。

## 13/16

还要分清控制手段：

CPU 上限：限制单次计算。

业务限流：限制操作。

预算提醒：通知人。

自动降级：减少后续暴露。

本次存在预算提醒，但没有验证完整响应链。

没有证明硬封顶，就别把告警叫“绝不会超过预算”。监测和生效都有延迟。

## 14/16

本地测试通过，也不是上线闭环。

要分别记录：本地完成、commit、部署版本、线上读回、观察窗口。

测试能证明重复票不增加、验证码失败不落库；不能靠桩和本地缓存，证明云平台不会收费。

这次线上版本和源码映射存在缺口，事后还原因此更难。

## 15/16

我整理了一套本地材料：

事故长文、脱敏证据、成本审查 skill、AGENTS.md 规则、项目模板和传播稿。

目的不是规定大家都用 R2/DO，而是要求开发前画请求路径、算正常与异常成本，上线后验证收费边界。

AI 编程交付应该同时包含功能模型和成本模型。

## 16/16

这次最该留下的教训：业务防刷、服务容量、费用控制，要分别验收。

验证码不能替调用预算签字，缓存不能替费用保护签字，页面能打开也不能证明运营安全。

全文和数字见同仓库 `articles/incident-review.md`、`evidence/case-facts.json`。发布时保留口径说明。
